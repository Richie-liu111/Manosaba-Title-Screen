# 还原原游戏标题画面布局 —— 实施计划

## 背景

当前 forge-1 使用 1920×1080 虚拟画布 + BUTTON_SCALE=0.6 + 左下角横排按钮，这是自行设计的布局。

原游戏（魔法少女ノ魔女裁判）使用的是 **2560×1440 参考分辨率**（来自解包数据中 CanvasScaler 的 `m_ReferenceResolution: {x: 2560, y: 1440}`），按钮以画布中心为锚点、散布在画面下半部、呈 zigzag 排列。

目标：把 forge-1 的布局改成和原游戏一样。

---

## 核心思路：只改一个数字 + 一堆坐标

`VirtualScreen` 类已经做好了坐标映射的工作：

```java
// VirtualScreen.java — 这一行决定了设计空间的分辨率
public VirtualScreen(int virtualWidth, int virtualHeight) { ... }

// 所有渲染坐标都经过这个转换：
toPracticalX(x) = currentX + x * practicalWidth / virtualWidth
toPracticalY(y) = currentY + y * practicalHeight / virtualHeight
```

所以把 `new VirtualScreen(1920, 1080)` 改成 `new VirtualScreen(2560, 1440)` 之后：

- 在 1920×1080 的屏幕上，virtual→practical 缩放比自动变成 `1920/2560 = 0.75`
- 这个 0.75 恰好就是原游戏 Unity CanvasScaler 在 1080p 屏幕上的缩放比
- 所有原游戏的坐标可以直接用！不需要手动乘 0.75

**唯一要改的文件**：`ManosabaTitleScreen.java`

### 5. TitleLogo 位置（第 97-105 行）

原游戏数据：AnchorMin=(0.5,0.5)、Pivot=(0.5,0.5)、AnchoredPosition=(747, 381)。

在 Unity Y-up 坐标系中，Logo 中心 = 画布中心 (1280,720) + 偏移 (747,381) = **(2027, 1101)**。

转换到 Minecraft 的 Y-down 坐标系：Y = 1440 − 1101 = **339**。Logo 中心 = **(2027, 339)**。

> **关于 160px 左移**：原游戏 Exit 按钮右边界在 x≈2717，超出了 2560 的 canvas 宽度。在 forge-1 中，Scissor 裁剪会让 Exit 按钮的右边 ~158px 不可见。为了避免这个问题，所有元素（Logo + 5 个按钮）统一向左平移 160px。

Logo PNG 尺寸：1039×622。平移后计算左上角：

```
x = (2027 − 160) − 1039/2 = 1867 − 519.5 = 1347.5
y = 339 − 622/2 = 339 − 311 = 28
```

```java
// 改后
logoLayer = new Layer(TextureConst.TITLE_LOGO_JA,
        1347.5f, 28f, 1039, 622, 1f, 0f, VIRTUAL_SCREEN);
```

边界检查：右边界 1347.5+1039=2386.5 < 2560 ✓，下边界 28+622=650 < 1440 ✓。

```java
private void initButtons() {
    String[] names = {"LoadGame", "NewGame", "Gallery", "Options", "Exit"};
    float[] xs = {1120f, 1463.5f, 1775f, 2037f, 2280.5f};
    float[] ys = {384.5f, 348.5f, 449.5f, 418f, 496f};
    int[] widths = {498, 437, 362, 338, 277};
    int[] heights = {323, 301, 251, 230, 190};

    for (int i = 0; i < names.length; i++) {
        String name = names[i];
        ResourceLocation normal = buttonTexture(name, false);
        ResourceLocation highlighted = buttonTexture(name, true);
        TitleScreenButton button = new TitleScreenButton(
                xs[i], ys[i], widths[i], heights[i],
                normal, highlighted, VIRTUAL_SCREEN, 0f);
        button.setDelay(UI_DELAY);
        button.setDuration(UI_DURATION);
        button.setAlphaFunction((t, now) -> t);
        button.setClickSound(clickSoundFor(name));
        button.setOnClick(b -> onButtonClick(name));
        addChild(button);
        addWidget(button);
    }
}
```

### 7. 背景缩放动画修正（`renderBackgroundCrop` 方法）

当前代码有个概念性问题：背景纹理是 4096×2048（2:1），但目标画布是 16:9。直接按画布比例算 UV 会导致背景图被横向压扁。

修正方案：始终从 2:1 纹理中裁剪出一个 16:9 的区域，再通过缩放做呼吸动画：

```java
private void renderBackgroundCrop(GuiGraphics guiGraphics) {
    float zoomScale = backgroundLayer.getScale();  // 1.1→1.0
    float alpha = backgroundLayer.getAlpha();

    // 背景纹理 4096×2048 (2:1)，目标 16:9
    // 使用全高，裁剪宽度：2048 * 16/9 = 3640.9
    // UV 宽度占比：3640.9 / 4096 = 0.8889
    float BASE_CROP_U = 0.8889f;
    float cropFraction = BASE_CROP_U / zoomScale;  // zoom越大→crop越小→画面越窄→放大感
    float uOffset = (1f - cropFraction) / 2f;
    float texU0 = uOffset;
    float texU1 = 1f - uOffset;

    RenderSystem.setShaderTexture(0, TextureConst.BACKGROUND);
    RenderSystem.setShader(GameRenderer::getPositionTexShader);
    RenderSystem.setShaderColor(1.0F, 1.0F, 1.0F, alpha);

    float px = VIRTUAL_SCREEN.toPracticalX(0);
    float py = VIRTUAL_SCREEN.toPracticalY(0);
    float pw = VIRTUAL_SCREEN.toPracticalWidth(2560);
    float ph = VIRTUAL_SCREEN.toPracticalHeight(1440);

    // ... 画 quad，UV 用 (texU0, 0) (texU0, 1) (texU1, 1) (texU1, 0)
}
```

### 8. render() 中的硬编码值

`render()` 方法里有 `1920 / scale`、`1080 / scale` 等硬编码，全部替换为 `2560`、`1440`。

版本号位置：当前是右下角偏移 `(−60, −24)`，在 2560×1440 空间下可以直接按比例调位置。由于 VirtualScreen 的 `currentX`/`currentWidth` 是运行时计算的，版本号的定位代码实际上不需大改——它已经在用 `currentX + currentWidth` 这些动态值。

## 为什么这个方案靠谱

1. **VirtualScreen 机制是正确的抽象**。它做的就是 Unity CanvasScaler 做的事。改了 virtual 分辨率之后，所有 position/scale 计算自动生效。
2. **坐标数据来自解包**。不是目测、不是猜测，是原游戏 prefab 里的精确数值。
3. **只改一个文件**。风险可控，回滚容易。
4. **160px 左移是唯一的手动调整**。原因是对 forge-1 的 scissor 裁剪边界的妥协——原游戏 Unity Canvas 可以设置 overflow 容忍，forge-1 的 scissor 不行。这个平移不影响相对布局。
5. **之前的分析已确认**：碰撞检测、按钮纹理、动画时序都和原游戏一致，不需要改。
